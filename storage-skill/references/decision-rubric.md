# 存储选型决策规则

> 来源：2025快手四大存储选型标准 + 25快手存储健康度治理&业务存储架构演进

## 第 0 步：硬约束（先判断，不进打分）

任一条件命中即为"硬性排除"或"硬性要求"，不得仅凭分数绕过：

| 场景特征 | 硬性结论 |
|---|---|
| 强一致事务主记录 + 数据量 < 5T | 必须使用 KSQL |
| 数据量 > 5T 或列数 > 200 | 必须使用 KTable，排除单机 KSQL |
| 全文检索或相关性排序 | ES 必须进入候选；ES 不得作为强一致主账本 |
| 高吞吐持续事件流 (> 万/s 量级) | Kafka 或 BTQ 作接入层，不直写 KSQL/KwaiBase |
| 大规模列式聚合分析 | CK 或 Doris；不用 KSQL/KwaiBase/HBase |
| bitmap 圈选人群 | 优先 Doris（Bleem） |
| 多表 Join 复杂查询 | 优先 Doris（Bleem）；评估是否能替代 CK |
| 超大规模向量检索 | Milvus；有少量全文检索需求可用 ES |
| 在线/近线宽表场景 | 优先 KwaiBase；禁止新增使用 HBase 在线集群 |
| 离线大数据宽表场景 | HBase 可用；在线场景严禁 |
| 图关联关系查询 | KGraph |
| 无共享海量二进制文件 | BlobStore（对象存储） |
| 需共享+低延迟随机 IO | KFS（文件存储） |

## 第 1 步：快手官方选型决策树（2025 版）

### 数据库 / 缓存

```
有持久化事务需求？
  是 → 数据量 < 5T 且列数 ≤ 200？
         是 → KSQL
         否 → KTable 2.0
  否 → 是否需要持久化？
         否 → 访问密度 > 1000/GB？
                是 → Redis
                否 → 有热 key/大 key 问题？
                       是 → KCache
                       否 → KCache（成本更低）
         是 → 访问密度 < 300/GB + 成本优先？
                是 → Kiwi（KwaiKV）
                否 → Redis 或 KCache
图数据 → KGraph
```

### 数据分析

```
全文检索/倒排索引 → ES
多表 Join / 多维分析 / bitmap 圈选 → Doris（Bleem）
超大规模列式聚合（已有 CK 集群可继续） → CK 或 Doris 评估替代
复杂业务计算 → JavaTask
简单周期/一次性任务 → 天工工作流
异构存储同步 → 天工数据同步
Hive 数据加工 → HiveSQL
```

### 文件 / 对象 / 块存储

```
海量二进制文件（图片/视频/软件包），无目录结构要求 → BlobStore
共享 + 目录结构 + 高吞吐顺序读写 → HDFS
共享 + 目录结构 + 低延迟随机读写 / 需要文件系统挂载 → KFS
单机存储 → KBD（块存储）
```

### 向量检索

```
大规模向量检索（在线推荐/召回） → Milvus
日志 + 少量全文检索 → ES
多模态数据存储 → 数据湖 + Bleem
```

## 第 2 步：矩阵打分维度

> 通过硬约束后方进行量化打分。

| 维度 | 权重 | 打分方法 |
|---|---|---|
| 数据模型匹配 | 20 | 数据结构（关系/KV/宽表/文档/图/时序）与候选契合度；完全匹配 18-20，基本匹配 12-17，需变形 6-11，不匹配 0-5 |
| 一致性与事务保障 | 20 | 强事务满分 20；最终一致 12-16；弱一致 6-11；无事务保障 0-5 |
| 查询/访问模式 | 15 | 主要访问路径（点查/范围/全文/聚合）与产品原生能力匹配度 |
| 性能目标 | 15 | 参照公司测试数据（Redis 10w+ QPS 亚毫秒；KCache 5w+ QPS；Kiwi 1w+ QPS 毫秒级；KSQL <1s 慢查）与需求对比 |
| 扩展性 | 10 | 能否以现有平台机制（分片/分区/副本）满足未来 3 倍增长 |
| 可用性与容灾 | 10 | 副本、AZ 覆盖与 RTO/RPO 要求；参考公司容灾标准（建议主备覆盖 100%、AZ 配平） |
| 存储成本 | 5 | 参照公司报价（Kiwi 最低 ~0.32¥/GB，KCache ~2.04¥/GB，Redis ~4.28¥/GB），以平台最新报价为准 |
| 团队运维能力 | 5 | 团队是否有该产品运维经验；参考公司治理计划（KTable 1.0→2.0 升级等） |

## 第 3 步：关键阈值红线（判断候选是否会立即触犯红线）

| 产品 | 红线阈值 | 说明 |
|---|---|---|
| KSQL | 大库 >1TB / 大表 >50GB / 副本 >4 / 慢查 >1s | 健康度治理目标 |
| Redis | 大 key >10KB / 热 key >10w/s / 逐出 >0 | 77 个大 key 在治理中 |
| KCache | 利用率 >85% / QPS 超上限 | 219 个集群在治理中 |
| Kiwi | 单分片 >50GB / 容量 >80% / 集群 >100TB | 37 个集群在治理 |
| ES | 分片 >50GB / 堆内存 >85% / 查询峰值 >10s | 39 个高危集群在治理 |
| KwaiBase / HBase | 在线场景使用 HBase | P1 故障已有记录 |
| KTable | 磁盘 >70% / CPU >90% | KTable 1.0 无告警须接入天问 |
