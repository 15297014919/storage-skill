# 反模式检查 Prompt

> 在给出推荐前，逐条检查下列快手内部真实反模式。命中任一条，须在报告的"已识别风险与反模式"中明确描述、给出风险等级（P0/P1/P2）并提供规避建议。

---

## A. KSQL（关系型数据库）

- [ ] **大库大表**：单库 >1TB 或单表 >50GB（已知 270+ 大库、600+ 大表在治理中）
  - 风险：OOM、主从延迟、扩容难度高
  - 建议：归档历史数据、分表分库或迁移 KTable

- [ ] **副本堆积**：副本数 >4 个
  - 风险：主从延迟飙升，运维成本翻倍
  - 建议：降至 ≤4 副本

- [ ] **日志流直写**：高频写入非事务日志到 KSQL
  - 风险：I/O 压力与写放大
  - 建议：Kafka 接入 + 落 CK/Doris

- [ ] **深翻页**：OFFSET 超 1 万行
  - 风险：全表扫描降级
  - 建议：改用游标（keyset pagination）

- [ ] **跨 DB JOIN**：生产环境跨数据库连接
  - 风险：不可拆库
  - 建议：应用层聚合

- [ ] **大字段**：TEXT / BLOB > 1MB 与其他列混排
  - 风险：行格式膨胀，缓冲池命中率下降
  - 建议：垂直拆表

---

## B. KV 缓存（Redis / KCache / Kiwi / Memcached）

- [ ] **大 Key**：Redis 单 key >10KB（已知 77 个大 key 在治理中）
  - 风险：序列化阻塞（Redis 单线程），网络带宽爆表
  - 建议：Hash 分片、局部获取或迁 KCache

- [ ] **热 Key**：Redis 热 key >10w QPS（已有集群超 20w QPS）
  - 风险：单核瓶颈、RT 飙升
  - 建议：LocalCache + 随机过期、迁 KCache（多线程抗热点）

- [ ] **Redis 逐出 >0**：内存使用率接近 100%
  - 风险：随机驱逐丢数据（已知 232 个集群使用率 ≥100%）
  - 建议：即时扩容或清理冷数据

- [ ] **Kiwi 单分片 >50GB**（已知 37 个集群在治理中）
  - 风险：扩容效率低，单分片不支持分裂
  - 建议：提前预分片，不超过 50GB/分片

- [ ] **Kiwi 集群 >100TB**
  - 风险：扩容缓慢，稳定性风险
  - 建议：拆分为多个独立集群

- [ ] **Kiwi 写延迟敏感场景**：写入速度要求高（写延迟毫秒级）
  - 风险：不满足写吞吐要求，尤其全量修复场景
  - 建议：改用 Redis 或 KCache

- [ ] **KCache 协议兼容**：使用了 KCache 不支持的 Redis 命令
  - 风险：静默错误或功能缺失
  - 建议：迁移前逐条检查兼容性文档

- [ ] **新增使用 Memcached**：公司方向是迁移至 Redis/KCache
  - 风险：技术债积累，运维重复
  - 建议：新场景直接使用 Redis 或 KCache

---

## C. 宽表（KwaiBase / HBase）

- [ ] **在线场景用 HBase**：在线/近线业务继续使用 HBase（HBase 已维护状态，2024 底 P1 故障）
  - 风险：P0 可用性事故
  - 建议：立即评估迁移至 KwaiBase

- [ ] **热点 RowKey**：RowKey 使用时间戳前缀、自增 ID 或用户 ID 未散列
  - 风险：Region 热点写，部分 Server 过载
  - 建议：加散列前缀（MD5/CRC 取模）

- [ ] **复杂二级索引**：宽表上做多维度任意组合查询
  - 风险：HBase/KwaiBase 不支持，需全表扫描
  - 建议：宽表 + ES 协同

---

## D. 搜索（ES）

- [ ] **ES 作强一致主记录**：订单/账单/资金流水写入 ES 为唯一权威
  - 风险：近实时可见性（约 1s 延迟），写入失败无事务回滚
  - 建议：以 KSQL 为主记录，ES 为搜索投影

- [ ] **大分片 >50GB**（已知 39 个高危集群在治理中）
  - 风险：写入/查询 RT 飙升，扩容/恢复耗时过长
  - 建议：分片 <50GB；单 Index 分片数 <200

- [ ] **堆内存 >85%**
  - 风险：频繁 Full GC，集群雪崩
  - 建议：扩容或减少映射字段

- [ ] **深翻页**：ES 默认 10000 行限制
  - 风险：内存与 CPU 爆增
  - 建议：使用 search_after 或 scroll

- [ ] **ClickHouse on ES**
  - 风险：已有 P4 故障案例
  - 建议：评估 Doris 或原生 CK 替代

- [ ] **ES 未配置天问告警**
  - 风险：故障无感知
  - 建议：必须接入天问告警

---

## E. OLAP（CK / Doris）

- [ ] **小批频繁写入 CK**：写入频次 >1 次/秒的小批量
  - 风险：Part 文件碎片爆炸，后台 Merge 过载
  - 建议：攒批写入（建议 >5w 行 或 >5s 间隔）

- [ ] **CK 高基数无界 GROUP BY**
  - 风险：内存 OOM
  - 建议：引入预聚合物化视图或限制基数

- [ ] **Doris 未按分区分桶设计**
  - 风险：查询扫描全量数据
  - 建议：明确分区键和分桶数

- [ ] **CK 新场景未评估 Doris（Bleem）替代**
  - 说明：2025 年 Doris 已具备替换 CK 的能力，建议评估
  - 建议：对新 OLAP 场景先用 Doris，并对比多表 Join 性能

---

## F. 消息队列（Kafka / BTQ）

- [ ] **消息积压无监控**：Kafka/BTQ 消费延迟堆积
  - 风险：P1 可用性故障（已知高危指标）
  - 建议：接入天问/自研监控，配置积压告警

- [ ] **缺少幂等+死信处理**
  - 风险：消息重复消费或永久丢失
  - 建议：消费端幂等 + 死信队列 + 报警

- [ ] **分区键设计不当**：分区键低基数或为空导致热分区
  - 风险：单分区消费瓶颈
  - 建议：分区键选高基数字段

---

## G. 通用跨产品反模式

- [ ] **缓存与数据库同步异常**：缓存先删 DB 再更新，无回滚机制
  - 建议：先更新 DB，再删缓存；或 Canal 异步投影

- [ ] **跨产品强依赖**：事务跨 ES + KSQL 且期望原子性
  - 建议：KSQL 为主记录，异步回填 ES

- [ ] **告警缺失**：存储集群未接入天问告警
  - 建议：所有集群强制接入天问（KTable 1.0 集群均未接入，为已知问题）

- [ ] **选型时未说明内部产品名**：报告使用"MySQL""HBase""ClickHouse"而不是"KSQL""KwaiBase""CK"
  - 建议：统一使用内部产品名，避免外采误解
